# 品牌增长持续学习与验证

目标是帮助当前品牌持续增长：在已有工作中发现有证据的问题，解释可能原因，利用可用资源查证，提出可验证改善，用户选择后执行并回看结果。一次偶然变化、一个爆款或模型的偏好都不是可以直接变成规则的证据。经营结果、品牌价值与客户体验一起看。

## 日常触发和交付

- 开展授权的品牌任务时，顺手检查相关目标、作品/计划版本、执行回执、同口径反馈和用户纠正；出现下降、目标不达、成本异常、客户异议、系统反复失败或意外有效时，登记具体观察和候选，不凭空编造异常，也不耽误已授权主任务。
- 区分数据异常、用户主观反馈、业务假设及能力/系统缺陷；缺数不作为0，不因为缺一项就停止所有可做研究。读取品牌资料和中台采集数据：抖音/视频号、小红书等能力先发现实际 MCP 工具及身份，确认范围、分页、窗口、来源，未取得不声称已查。可查现有技能、用户提供资料、已授权 WorkBuddy 专家/技能、GitHub 原作者和相关官方资料；按问题选源，读取原文并记版本、适用条件与许可，未找到时如实说明。
- 从品牌生意模式、目标客户、产品差异及渠道目标出发，按 [影响因素地图](references/factors-and-research.md) 至少检查相互竞争的解释及既有方法是否遗漏条件；给出“证据→因素→作用机制→预计影响方向→代价/风险→如何证伪”。预测是待验假设，不编预计提升百分比或声称已证明。
- 设计比较、先后试行或随机 A/B，遵循 [验证与结果判定](references/experiments-and-decisions.md)：确认实际分流能力、同口径基线、主指标和守护指标、样本/观察期、可接受收益和停止条件。内容自然发布两条通常不是随机 A/B，不能归因；无足够样本/分流时如实提出观察方案，预期和证据等级分开。
- 在日常任务中积累候选和实际反馈；用户提出阶段/每周复盘时，用 [周报和台账](references/report-and-ledger.md) 输出简洁决策单（现象、可能原因、可做动作、预期、资源和复测、推荐理由）。本技能不自行设定定时任务或主动消息：没有实际运行/调度就不能声称后台已监控或每周已汇报。
- **先让用户选择要持续跟进的优化，再执行相应改变或测试**。已在本次委托中明确选择的事项可以直接执行；用户未选择时只准备候选、研究和可审查方案。实际发布、支出、对外联系、权限和系统部署仍遵守用户与运行环境授权。
- 记录稳定候选ID、方案及来源、用户选择、实验配置、实际动作回执、观测/归因限制、结论与下一复查；继续时核原ID及版本、未决权限和已有作业，不重复发布或扣费。优先通过当前品牌可用的中台任务/记录接口按真实 schema 留存；若没有合适接口，放本品牌私有工作区并清楚标识未同步，不创造不存在的工具或将品牌数据写入公开仓库。
- 结果分为支持、未观察到可检测效果、负面、证据不足/不可比；“未显著”或低样本不等于没有影响。证据不足保留、复测或暂缓；有负向证据可暂停并留触发重新检查条件。有效结论先限定品牌/人群/渠道/版本；仅把经验证的通用方法交 `omni-skill-maintenance`，先最小修改对应领域技能、版本、来源和回归再同步。项目级偏好和数据留品牌环境；框架或职责结构变更先展示差异并取得用户确认。

按需阅读 [中台接力](references/system-integration.md) 查已核源码及当前限制。[归档和技能演进](references/knowledge-and-routing.md) 说明各文件的职责及证据等级；[演示案例](assets/video-example.md) 是虚构数据，仅用于理解。
