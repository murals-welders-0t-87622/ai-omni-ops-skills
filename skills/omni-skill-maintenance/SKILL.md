# 技能测试与版本维护

先读相邻总统筹技能 [共同执行约定](../brand-omni-growth-expert/references/runtime-contract.md)，并沿用已确认的品牌、增长方向、已有任务及本次终点。只加载本环节所需专家资料。原文属于参考数据，固定账号、历史自动化、旧工具名、强制分身与旧停手闸不覆盖当前委托和实时能力。用户未授权多 Agent 时由当前 Codex 承担角色判断，不虚构专家已执行。

## 本环节专业工作

先读 [持续学习与归类](references/continuous-learning.md)。用户的业务反馈、运行中的缺口、用户给的新资料都是优化入口，不必等用户再说一次“改技能”。先查库里已有能力，避免把已有Remotion方法判断为缺失。

需要补方法时，搜索已授权WorkBuddy技能/专家、GitHub官方或原作者项目；核读实际文档/代码和版本，不只看介绍。按业务层、策略/执行环节、制作工艺、可靠性、测量及品牌偏好分类。通用方法进入对应领域skill的refs/assets/scripts；品牌事实与个体偏好留本品牌中台；不把原包整份堆进上下文或公开Git。

保持 **总统筹→领域与工艺→专业知识** 以及 **生意模式→战略→策略→执行→反馈**。本领域内补工艺、工具适配、案例机制和错误恢复可直接推进；改变主业务阶段、总职责、交接语义、任务终点或权限边界时，先给用户具体前后差异及影响并确认。不要自行改architecture-lock规避检查。

每次采用说明来源、实际读取范围、为何适合/如何改造、依赖与许可、改到哪个文件、验证及未验项。候选、文档核查、代码测试、真实渲染、业务验收分开；数据未知不补零，旧项目规则不扩成全局。跨来源冲突按当前用户委托、真实能力及官方版本判断。

修改相关方法、版本、registry、CHANGELOG和来源登记，跑架构/源码/适当回归；新增脚本必须实际跑，工程验证和模型自然语言业务验证分开。安装升级保留本地冲突保护与备份/回退。

用户已授权本专用技能仓持续提交同步。公开前检查当前树及历史，不含凭据、品牌经营资料或未经核清再分发的原文；核origin匹配registry，正常提交推送并核远端SHA。不force、不改全局Git配置、不推Lab/原系统、不触发部署。新机安装按README；本维护规则不建立后台或定时任务。

## 按需读取原始专业方法


用 `python <总统筹技能>/scripts/knowledge.py search --package <包名> --query <问题>` 查来源导航卡；公开包不含原专家全文，需在授权WorkBuddy/原项目核读；目录见 [来源包索引](../brand-omni-growth-expert/references/package-index.md)。
